# ADR-0004: Набор символов ника

## Статус

Принято (2026-11-26).

## Контекст

`POST /v1/accounts` с ником `нет-такого` проходил проверку длины, записывал строку учётки и ставил заголовок `Location` с этим ником. Kestrel отвергает не-ASCII в значении заголовка. `AccountExceptionMiddleware` превращал это необработанное исключение в `503` `store_unavailable`. Ручной прогон `specs/005-postgres-profile-auth/manual-test.md` остановился на шаге 18: учётка уже была в таблице, а клиент видел недоступное хранилище.

Спецификация до этой правки не ограничивала алфавит ника. Код `nick_invalid` описан для создания. Неуспешный вход остаётся одним кодом `sign_in_failed`: контракт, модель данных и research прямо не используют `nick_invalid` на входе.

## Решение

Ник после снятия краевых пробелов состоит только из английских букв `A–Z`/`a–z`, цифр `0–9` и знаков, которые спецификация ника уже принимает: пробел, апостроф `'`, кавычка `"`, точка с запятой `;`, дефис `-`.

Любой другой символ, включая букву другого алфавита, на создании даёт `nick_invalid` до транзакции. Строка учётки не пишется, заголовок `Location` не ставится.

На входе тот же символ не открывает доступ и не читает строку учётки, даже если она уже лежит в таблице. Ответ — `sign_in_failed`, не `nick_invalid`. Для ника допустимой длины пишется прежняя строка журнала оператора о неудачном входе.

Кодировка `Location` и отображение `503` не меняются.

## Последствия

- Контракт `account-api.yaml` — версия документа 1.1.0, префикс маршрутов `/v1`.
- Уже сохранённый ник вне набора входом не открывается. Новая миграция и CHECK в базе не добавляются: правка — отказ до записи, а не смена схемы.
- Пароль и отображаемое имя по-прежнему не ограничены этим набором.
