# Research: Профиль учётной записи и авторизация класса C

Дата: 2026-11-19. Все неизвестные Technical Context закрыты здесь. Маркеров `NEEDS CLARIFICATION` в плане не остаётся.

## 1. Второй одновременный доступ одного ника

**Decision**: Новый вход не отзывает предыдущий. У одного ника может быть несколько живых доступов. Завершение доступа гасит только тот доступ, которым человек его завершил. Истечение 12 часов считается отдельно для каждого. Смена пароля не гасит ни один живой доступ, включая тот, из которого пароль сменили.

**Rationale**: Спецификация говорит о доступе после входа и о том, что человек завершает доступ отдельным действием. FR-011 прямо оставляет тот же доступ живым после смены пароля. Журнал различает источники двух входов, значит два входа — нормальный случай, а не ошибка. Отзыв предыдущего входа был бы новым правилом, которого в спецификации нет. Класс C2 здесь про подотчётность и доступ только владельца, а не про одну сессию на человека. Окно украденного доступа и так ограничено 12 часами и явным завершением.

**Alternatives considered**: «Новый вход заменяет предыдущий» — проще для отзыва, но завершает доступ, который человек не завершал, и расходится с независимым сроком «после входа». «Один живой доступ, второй вход получает отказ» — этого кода нет в FR-023, и второй свой вход нельзя честно назвать ни неуспешным входом, ни чужими данными. Отложить выбор нельзя: без него не задать носитель доступа, а незакрытое уточнение для плана — ошибка.

## 2. Носитель доступа

**Decision**: При входе в таблицу `access` пишется строка (`access_id`, `account_id`, `issued_at`, `ended_at`). `expires_at` не хранится. Доступ действует, пока `ended_at` пусто и `now < issued_at + 12 часов`. Момент выдачи обрезается до целой секунды UTC. Вызывающей стороне отдаётся JWT HS256: `iss` и `aud` равны `kanban-account`, `sub` — id учётки, `jti` — id доступа, `iat` и `exp` в секундах, `exp = iat + 43200`. Допуск часов (`ClockSkew`) — ноль. Подпись проверяется, затем строка читается из базы. База решает, жив ли доступ: раннее завершение без строки невозможно. Ключ подписи — переменная окружения `KANBAN_JWT_SIGNING_KEY`, не короче 32 байт. В репозитории ключа нет. Нет refresh-токена. Повторный вход — новый JWT и новая строка.

**Rationale**: Конституция называет JWT целевым носителем. Одного JWT мало: FR-007 требует завершить доступ раньше срока. Счётчик поколения на учётке гасил бы все доступы сразу и сломал бы и решение 1, и FR-011. Хранить `expires_at` рядом с `issued_at` нельзя: срок всегда вычисляется из времени входа, отдельная колонка нарушила бы BCNF и FR-024. Пятиминутный допуск по умолчанию у JwtBearer сделал бы доступ длиннее 12 часов, поэтому он обнулён, а сверка с базой обязательна.

**Alternatives considered**: Только серверная сессия без JWT — хуже стыкуется с целевой архитектурой. Только JWT со списком отозванных `jti` — тот же состояние в базе, но легче забыть проверку. ASP.NET Identity cookie — приносит нормализацию имени и другой жизненный цикл, ломает точный регистр ника.

## 3. Принцип III и FR-023

**Decision**: Тело отказа — объект `{"code":"<устойчивый код>"}` и ничего больше. ProblemDetails, `title`, `detail`, `message` и текст исключения в ответ не попадают. Русская фраза каждой ситуации написана в описании контракта и явно помечена как документация, а не как тело ответа. CLI не вызывает этот API и сохраняет свой ненулевой код и человекочитаемое сообщение. Нарушение буквальной формулировки III для тела HTTP обосновано в Complexity Tracking плана. Конституция не правится.

**Rationale**: Один и тот же ответ не может одновременно содержать человеческую фразу и не содержать её. Спецификация уже принята. Governance разрешает явное обоснование в плане. Прятать конфликт за пересказом принципа нельзя.

**Alternatives considered**: Фраза в JSON — нарушает FR-023. Пустой ответ только со статусом HTTP — `ник недопустим` и `пароль недопустим` оба стали бы 400 и перестали различаться. Смена конституции из plan — вне этой команды.

## 4. Каталог кодов и статус HTTP

**Decision**: Код в теле — контракт. Статус HTTP вторичен и не заменяет код.

| Код | HTTP | Когда |
| --- | --- | --- |
| `nick_taken` | 409 | Повтор ника при создании, в том числе гонка |
| `nick_invalid` | 400 | Создание: ник пустой, из пробелов или длиннее 64 |
| `password_invalid` | 400 | Создание или смена: новый пароль пустой или длиннее 1024. Не вход |
| `sign_in_failed` | 401 | Любой неуспешный вход: нет ника, неверный пароль, пустая пара, слишком длинное поле. Один код |
| `no_active_access` | 401 | Нет токена, битый токен, чужая подпись, срок вышел, доступ завершён |
| `foreign_data` | 403 | В токене один ник, в пути другой. Существование цели не раскрывается |
| `display_name_invalid` | 400 | Имя пустое, из пробелов или длиннее 128 |
| `password_change_rejected` | 403 | Текущий пароль не назван или неверен. Новый при этом допустим |
| `store_unavailable` | 503 | База недоступна или транзакция не зафиксирована |
| `request_invalid` | 400 | Тело не той формы, не JSON, не строки, больше 16 КиБ |
| `card_invalid` | 400 | Пустой заголовок, срок не `YYYY-MM-DD`, повтор метки без учёта регистра |
| `object_missing` | 404 | Своя колонка или своя карточка не найдены. Чужие id не ищутся |

Порядок на входе: нет живого доступа → `no_active_access`, и путь ещё не смотрится. Ник пути не равен нику доступа → `foreign_data`, даже если такого ника нет. Дальше проверка формы и только потом запись. На входе коды `nick_invalid` и `password_invalid` не используются. Если базы нет в момент, когда без неё нельзя решить, ответ `store_unavailable`, а не `sign_in_failed`: иначе сбой журнала выглядел бы как обычный неверный пароль и событие FR-017 потерялось бы.

**Rationale**: FR-023 задаёт девять ситуаций. Ещё три кода нужны, чтобы отказ доски и битое тело не притворялись этими девятью и не превращались в английский ProblemDetails. Проверка формата нового пароля идёт до сверки текущего: состояние не меняется в обоих случаях, а код совпадает со сценарием «новый пароль пустой».

**Alternatives considered**: Один код `validation_failed` на все 400 — сотрёт различия FR-023. Идемпотентный 204 на удаление чужого id без кода — не нужен для колонки, которой нет; вызывающей стороне нужен устойчивый отказ, поэтому `object_missing`.

## 5. PostgreSQL отдельным контейнером и Dockerfile в CD

**Decision**: Сервис `postgres` в `docker-compose.yml` собирается из `docker/postgres/Dockerfile` (`FROM postgres:17`). Процесс API в этот образ не входит. Оператор поднимает хранилище одной командой `docker compose up --build postgres`, не стартуя API. CD-архив `kanban-win-x86.zip` дополнительно получает корневой `Dockerfile`, `docker/postgres/Dockerfile` и `docker-compose.yml`. Публикация win-x86 и правило «GitHub Release только на тег `v*.*.*`» не меняются. Тег эта фича не ставит.

Роли базы, пароли только из окружения, без значения по умолчанию в файлах:

- `kanban_migrator` — владелец таблиц, применяет миграции;
- `kanban_app` — соединение API: DML учётки и доски, INSERT журнала, без UPDATE/DELETE журнала и без SELECT журнала неизвестных ников;
- `kanban_operator` — только SELECT журнала неизвестных ников.

Образ API по-прежнему собирается корневым `Dockerfile` и не содержит копию базы.

**Rationale**: FR-021 требует компонент, который запускается отдельно, из материалов поставки. Уже существующий `Dockerfile` описывает API, не базу. Официальный образ PostgreSQL 17 поддерживается отдельно от жизни процесса API. Мажорный тег `17`, не `latest`, чтобы поставка не перескакивала на следующую основную версию сама. Владелец таблицы обходит GRANT, поэтому роль приложения не должна владеть таблицами: иначе отзыв SELECT ничего не стоит.

**Alternatives considered**: База внутри образа API — это не отдельный компонент. SQLite в файле рядом с API — переходное состояние, которое конституция запрещает закреплять. PostgreSQL 16 — старше без выигрыша. Не класть Dockerfile в zip — поставка win-x86 остаётся без описания сборки, хотя исходный запрос и FR-021 требуют материалы запуска.

## 6. Стек доступа к базе

**Decision**: EF Core 9.0.0 и провайдер Npgsql той же линейки 9.0.x. Не поднимать UserProfile и новую базу на EF 10 в этой фиче. JWT-пакет — 10.0.13, как уже зафиксированный пакет ASP.NET в `Kanban.Api`. Миграции — EF Core Migrations в `Account.Infrastructure`, с рабочим `Down`. API не вызывает `EnsureCreated` и не мигрирует схемой роли приложения. Старт без схемы даёт ошибку запросов и ответ `store_unavailable`, в логе это ошибка настройки, без строки подключения.

**Rationale**: В репозитории уже зафиксирован `Microsoft.EntityFrameworkCore.Sqlite` 9.0.0 при TFM `net10.0`. Вторая major EF в одном тестовом процессе, где остаётся ссылка на UserProfile, ломает сборку без пользы для сценария. SDK в сессии плана не был установлен, поэтому патч новее уже зафиксированного 9.0.0 не назначается наугад.

**Alternatives considered**: EF Core 10 сразу — ровнее к TFM, но это отдельное обновление двух баз и снимка старой миграции. Dapper — меньше магии и те же параметры, но миграции и транзакции пришлось бы собирать вручную рядом с уже принятым EF. `EnsureCreated` — так сделан старый профиль; для новой схемы это не миграция и не обратимо как версия схемы.

## 7. Хэш пароля

**Decision**: `PasswordHasher<object>` из `Microsoft.Extensions.Identity.Core`, формат Identity V3 (PBKDF2), параметры по умолчанию, без уменьшения итераций. В колонке `password_hash` лежит только эта строка. Открытый пароль не пишется ни в базу, ни в журнал, ни в лог, ни в ответ. Если ника нет, проверка всё равно вызывает `VerifyHashedPassword` на постоянном учебном хэше, который не принадлежит ни одной учётке. Это выравнивает ветки. Требование спецификации — один код, а не доказательство постоянного времени. Учебный хэш можно хранить в коде: он не открывает учётку.

**Rationale**: Конституция требует хэш и запрещает секрет в репозитории. Штатный hasher платформы не тянет за собой Identity-пользователя, который нормализует имя.

**Alternatives considered**: Полный ASP.NET Identity — см. решение 2. Argon2 или bcrypt отдельным пакетом — спецификация не выбирает алгоритм, а конституция не требует алгоритм сильнее хэша платформы. Свой SHA-256 без соли — не подходит.

## 8. SQL-инъекции

**Decision**: Запись и чтение учётки, доски и журнала — только LINQ и API EF, параметры которого передаёт провайдер. `FromSqlRaw`, `ExecuteSqlRaw` и склейка SQL со значением ника, пароля, имени или текста карточки запрещены. Защита нужна: эти значения спецификация велит хранить буквально, включая кавычки и текст, похожий на команду. Проверка — набор из 20 таких значений в quickstart и тестах: чужая учётка и чужая доска не меняются, своё значение читается обратно как введено.

**Rationale**: FR-016. «Если надо» здесь надо, потому что значение доходит до SQL. Параметры EF закрывают это без отдельного фильтра символов, который исказил бы буквальное хранение.

**Alternatives considered**: Запретить кавычки в нике — противоречит сценарию буквального хранения. Экранировать вручную — хуже параметров и легко ошибиться.

## 9. Нормализация BCNF

**Decision**: Схема из [data-model.md](data-model.md). Кратко: ник, имя и хэш — атрибуты учётки и ключа. Доска определяется учёткой один к одному и не хранит ник. Карточка хранит колонку, не доску: доска выводится из колонки. Метка — строка в своей строке, не справочник. Журнал владельца хранит `account_id`, не ник. Журнал неизвестного ника хранит попытку ника и не имеет `account_id`. `expires_at` нет. История паролей и имён нет. Удаление колонки и карточки физическое, без флага «скрыто». Имя удалённого объекта пишется в журнал в той же транзакции, что и удаление, и после фиксации живой копии уже нет.

**Rationale**: FR-024 запрещает два места, которые правят по отдельности. Функциональная зависимость `account_id → nick` сделала бы ник в журнале нарушением BCNF: определитель не является ключом события. Отдельная таблица неизвестных ников не позволяет позже проставить ей владельца. Вычисляемый срок — не второй факт. Мягкое удаление оставляло бы текст карточки читаемым в строке.

**Alternatives considered**: Одна таблица журнала с пустым `account_id` — тоже BCNF, но колонка так и просит заполнить её при будущей регистрации, что запрещает FR-019. JSON-доска в колонке учётки — повторяющаяся группа, не BCNF, и вторая копия рядом с файлом. Общий справочник тегов — правка метки одной карточки задевала бы другие.

Очистка понимается как наблюдаемое поведение FR-020, а не как аттестация носителя. Мёртвые кортежи PostgreSQL до VACUUM не считаются вторым ответом API. Отдельной перезаписи диска спецификация не требует: это не аттестация ОС.

## 10. Источник обращения

**Decision**: Источник — адрес TCP-узла запроса, без порта и без User-Agent. IPv4-mapped IPv6 приводится к IPv4. Иначе берётся каноническая строка `IPAddress`. Одинаковый адрес даёт одинаковую строку, разный — разную. Если адреса нет, источник — постоянная строка `unknown` (одинаковые такие запросы совпадают). Заголовок `X-Forwarded-For` не доверяется. Длина строки укладывается в 45 символов.

**Rationale**: Спецификация оставляет вид источника на план и требует, чтобы он не был паролем, различал разные источники и совпадал для одного. Порт меняется на каждом соединении и развалил бы «тот же источник». Пересылаемый заголовок клиент может подделать, и подотчётность пропадёт.

**Alternatives considered**: User-Agent — длинный, подделывается, может случайно содержать лишнее. Пара IP и порт — слишком дробная. Отдельное поле, которое клиент сам присылает, — не источник, а ещё один ввод.

## 11. Журнал: что пишется и кому видно

**Decision**: Типы событий: `sign_in`, `access_end`, `password_change`, `display_name_change`, `foreign_access_denied`, `column_deleted`, `card_deleted`. Результат: `success` или `failure`.

Пишется всегда по FR-017: успешный вход, неудачный вход, завершение доступа, смена пароля (и отказ из-за текущего пароля, и отказ из-за недопустимого нового — тип тот же, результат `failure`), смена имени (успех и недопустимое имя), отказ в чужих данных, удаление колонки, удаление карточки. Обычное чтение доски не пишется. Отказ регистрации (`nick_taken` и неверный формат) не пишется: его нет в FR-017.

Неудачный вход в существующий ник — строка журнала этой учётки. Неудачный вход в ник длиной 1..64, которого нет, — строка журнала оператора с этим ником, без пароля. Пустой ник и ник длиннее 64 на входе дают тот же `sign_in_failed`, но в журнал оператора не попадают: учёткой они быть не могут, а произвольный длинный текст в журнале не хранится. Тело запроса и так режется 16 КиБ.

Отказ в чужих данных пишется владельцу того доступа, которому отказали, без содержимого цели и без её доски. Жертва отдельную строку не получает: сценарий US4 привязывает событие к нику, который действует.

Удаление колонки пишет одну строку с именем колонки. Карточки колонки удаляются каскадом и в журнал поименно не копируются. Удаление карточки пишет заголовок карточки. Описание, метки и срок в журнал не входят.

Чтение своего журнала отдаёт ник соединением с учёткой, не из колонки события. Время — UTC до секунды, обрезка вниз.

UPDATE и DELETE по обеим таблицам журнала запрещены триггером для всех ролей. Снять запрет можно только миграцией, не действием профиля или доски.

**Rationale**: FR-017–FR-020. Причина отказа пароля в журнал не кладётся, чтобы не плодить второе поле. Имя удалённого объекта в журнале требуется спецификацией и после фиксации транзакции уже не дублирует живую карточку.

**Alternatives considered**: Писать отказ на журнале жертвы — полезно для неё, но спецификация так не говорит и легче утечёт факт, кого искали. Писать старое имя в журнал смены — нарушит FR-020, потому что чтение журнала вернуло бы заменённое имя. Мягкое удаление карточки — текст остаётся в базе и может вернуться.

## 12. Где живёт код и что не трогаем

**Decision**: Новые проекты `Account.Domain` и `Account.Infrastructure`. Маршруты `/v1` в `Kanban.Api`. `Kanban.Domain` не узнаёт про учётку. Доска владельца читается и пишется только в PostgreSQL. `data/board.json` остаётся у CLI и у переходного `/api/board` и не синхронизируется с доской учётки. `UserProfile.*` и SQLite не читаются и не пишутся этой фичей. Контракт `/profiles` не меняется.

Точка входа `Kanban.Api` делается видимой для `WebApplicationFactory` так же, как уже сделано в `UserProfile.Api` (`public partial class Program`). Тестовый проект получает ссылку на `Kanban.Api`.

**Rationale**: Два хоста для одной базы — риск второй копии. Третий хост — лишняя подсистема. Старый профиль по полям исключён допущением спецификации. Молча подменить `/profiles` запрещает принцип I.

**Alternatives considered**: Расширить `UserProfile` колонками ника — смешивает две модели и ломает опубликованный контракт. Хранить доску владельца в JSON «пока» — прямое нарушение FR-021 и конституции.

## 13. Сравнение, длина, обрезка

**Decision**: Длина ника, имени и пароля считается в кодовых точках Unicode (`Rune`), не в единицах UTF-16 и не в графемах. Ник и отображаемое имя: снять пробелы по краям (`char.IsWhiteSpace`), потом проверить пустоту и длину. Пробелы внутри остаются. Нормализация NFC/NFD не делается. Регистр ника не выравнивается. Уникальный индекс ника — `COLLATE "C"`. Пароль не обрезается; пароль из одних пробелов допустим. Заголовок и метки карточки не обрезаются. Пустой заголовок отвергается. Заголовок из пробелов допустим: он не пустой. Имена колонок и метки сравниваются `StringComparison.OrdinalIgnoreCase`, как продолжение ADR-0001, и это правило не применяется к нику. В базе уникальность колонки и метки дополнительно страхует индекс по `lower(...)` для латинского регистра; решающая проверка перед записью — порядковое сравнение без регистра в домене.

**Rationale**: Спецификация требует точный ник и отбрасывание краевых пробелов до проверки. `string.Length` рвёт суррогатные пары. NFC склеивала бы последовательности, которые спецификация велит сравнивать буквально. Культурный `ToLower` (турецкий I) сделал бы уникальность ника зависимой от локали сервера.

**Alternatives considered**: `citext` для ника — как раз без учёта регистра, это отвергнуто clarify. Грагфемные кластеры — зависят от локали и плохо проверяются в PostgreSQL `char_length`.

## 14. Операции доски, которые входят в фичу

**Decision**: Создать карточку в названной колонке (заголовок и необязательные описание, метки, срок), удалить карточку, удалить колонку. Колонки при регистрации: `ToDo`, `InProgress`, `Done`, позиции 0, 1, 2. Добавление и переименование колонки, перенос карточки, правка карточки и смена порядка внутри колонки не входят: спецификация запрещает новые виды действий и не требует здесь весь набор CLI. Порядок карточек в ответе — по `created_at`, затем по id; это устойчивость чтения, а не новое правило порядка. Имя доски не хранится и в контракт `/v1` не входит.

**Rationale**: Сценарии требуют положить карточку, прочитать поля принятой модели и удалить колонку или карточку для журнала. Перенос и фильтры в допущениях исключены.

**Alternatives considered**: Повторить весь CLI на HTTP — шире спецификации. Отдать доску только целиком через старый PUT `/api/board` — нет журнала на отдельное удаление и есть общая JSON-доска.

## 15. Операторский журнал без HTTP

**Decision**: Учётка продуктa не читает таблицу неизвестных ников. Роль `kanban_app` не имеет на неё SELECT. Оператор читает её ролью `kanban_operator`, команда — в [contracts/operator-audit.md](contracts/operator-audit.md). Отдельного входа офицера безопасности нет.

**Rationale**: Допущение спецификации: отдельной роли в продукте нет, а событие без владельца учёткам не показывается. HTTP-ручка с общим секретом была бы вторым входом в приложение. Отзыв SELECT закрывает случайную выборку из кода API.

**Alternatives considered**: `GET /v1/operator/journal` с паролем из окружения — ещё один контур доступа, его нет в FR-023. Одна роль базы на всех — ошибка или инъекция в API прочитала бы журнал без владельца.

## 16. Тесты и CI

**Decision**: Интеграционные тесты поднимают PostgreSQL через Testcontainers и прогоняют миграции ролью владельца, а приложение подключают ролью `kanban_app`. Отдельный тест убеждается, что роль приложения не делает SELECT журнала неизвестных ников. Срок 12 часов и досрочное завершение проверяются через `TimeProvider`, без ожидания реального времени. CI остаётся `dotnet test kanban-cli/Kanban.sln` на `ubuntu-latest`: Docker раннеру доступен, отдельный сервис в workflow не обязателен. Если раннер когда-нибудь окажется без Docker, это ломает новый критический путь и чинится в реализации, а не подменой базы на SQLite.

**Rationale**: Принцип II требует тесты авторизации, записи и миграции. SQLite не проверяет `COLLATE "C"`, роли и каскад PostgreSQL.

**Alternatives considered**: Только модульные тесты hasher — не ловят гонку уникального ника и инъекцию. Общая база в CI сервисом workflow — тоже годится, но Testcontainers повторяет ту же проверку локально одной командой `dotnet test`.

## 17. Транзакции и частичная запись

**Decision**: Одна транзакция на регистрацию (учётка, доска, три колонки), на смену имени, на смену пароля, на создание карточки с метками, на удаление вместе с записью журнала, на вход (строка доступа и строка журнала). Сбой посередине откатывает всё. Ответ тогда `store_unavailable`. Повторный ник в гонке ловится уникальным индексом и становится `nick_taken`, а не частичной учёткой.

**Rationale**: FR-005 и FR-022. Журнал входа, который не зафиксирован, нельзя заменять ответом `sign_in_failed`.

**Alternatives considered**: Писать журнал после ответа — событие FR-017 теряется при обрыве. Отдельные автокоммиты на колонки — доска без `Done` при обрыве.
