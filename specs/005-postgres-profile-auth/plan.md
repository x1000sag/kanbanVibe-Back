## Summary

Человек заводит учётную запись с неизменяемым ником и паролем, входит и после этого читает свой профиль: ник, отображаемое имя и одну свою доску. Чужие данные недоступны, доступ нельзя передать, отказанный вход не различает отсутствие ника и неверный пароль, доступ живёт не дольше 12 часов. Учётки, доски и журнал лежат в PostgreSQL, который запускается отдельным контейнером. Приложение не держит вторую главную копию.

Технический ход, детали — в [research.md](research.md):

- Носитель доступа — подписанный JWT плюс строка доступа в базе. Срок 12 часов вычисляется из времени входа и в колонке не хранится. Досрочное завершение гасит только эту строку.
- Второй одновременный вход того же ника не гасит предыдущий доступ. Оба живы, пока каждый не истечёт или человек не завершит именно его. Смена пароля ни один из них не гасит.
- Отказ HTTP — только устойчивый код в поле `code`, без фразы для конечного пользователя. Русское объяснение кодов лежит в описании контракта: его читает вызывающий сервис. Это совпадает с принципом III конституции 3.0.0.
- Схема в BCNF: ник и хэш пароля только на учётке, имя только на учётке, журнал владельца ссылается на учётку и не копирует ник, журнал неизвестного ника — отдельная таблица без связи, которую можно было бы заполнить задним числом. Пароль в открытом виде не хранится и не пишется в журнал.
- Прежний `/profiles` (SQLite, почта и фото) и прежний `/api/board` (общий JSON) этой фичей не становятся хранилищем учётки. Молча их не ломаем и не читаем из них доску владельца.

На проверку человека до `speckit.tasks`: выбранное правило двух доступов и журнал оператора через роль базы, а не через HTTP. Расхождение III с FR-023 снято конституцией 3.0.0.

## Technical Context

**Language/Version**: C# / .NET, TFM `net10.0`, SDK из `global.json` (`10.0.404`, roll-forward `latestFeature`)

**Primary Dependencies**: ASP.NET Core (хост `Kanban.Api`); Entity Framework Core 9.0.0 и `Npgsql.EntityFrameworkCore.PostgreSQL` 9.0.x (та же линейка, что уже подключённый `Microsoft.EntityFrameworkCore.Sqlite` 9.0.0); `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.13 (как `Microsoft.AspNetCore.OpenApi` в `Kanban.Api`); `Microsoft.Extensions.Identity.Core` 10.0.13 (`PasswordHasher`, без полного ASP.NET Identity); xUnit и `Testcontainers.PostgreSql` 4.x в тестовом проекте. Точный патч Npgsql и Testcontainers фиксирует `packages.lock.json` на реализации. Патч в этот план не выдуман: SDK в сессии планирования недоступен.

**Storage**: PostgreSQL 17, отдельный контейнер. Образ `postgres:17` (мажор, не `latest`). Учётка, доступ, доска, карточки и оба журнала — в одной базе. JSON-доска и SQLite профиля — не источник этих данных.

**Testing**: xUnit, `WebApplicationFactory` для `Kanban.Api`, интеграционные тесты через Testcontainers.PostgreSql. Критический путь: регистрация и гонка ника, вход, отказ входа одним кодом, два одновременных доступа, завершение одного из них, срок 12 часов, чужие данные, смена имени и пароля, журнал, очистка заменённых значений, недоступность базы, буквальное сохранение текста с кавычками и обрывками SQL.

**Target Platform**: контейнер API (существующий корневой `Dockerfile`, Linux) и отдельный контейнер PostgreSQL. Публикация Windows x86 в CD сохраняется. CLI остаётся локальным клиентом JSON-доски и удалённый вход не получает.

**Project Type**: веб-сервис, только серверная часть. Контракт фронтенда не входит.

**Performance Goals**: отдельный SLO пропускной способности спецификация не задаёт. SC-001 — человек создаёт учётку и входит быстрее двух минут. Хэш пароля — штатные параметры Identity V3, без снижения числа итераций.

**Constraints**: ник неизменяем и сравнивается точно, с учётом регистра, без Unicode-нормализации; пароль — любое непустое значение 1..1024 кодовых точек, без правил состава и без обрезки; доступ строго короче либо равен 12 часам, допуск часов JWT равен нулю; группы и передача доступа отсутствуют; SQL только параметризованный (LINQ EF), без склейки строк; секреты не в репозитории; тело отказа без текста для человека; тело запроса на методах этой фичи не больше 16 КиБ.

**Scale/Scope**: все истории и FR-001–FR-024. Одна доска на учётную запись. Несколько досок, группы, смена ника, удаление учётки, восстановление пароля и блокировка после ошибок не входят.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Прочитана конституция `.specify/memory/constitution.md`, версия 3.0.0 (ратификация 2026-10-28, поправка 2026-11-20). Проверка ниже заново сверена с этой версией. Первая запись ворот ссылалась на 2.0.0 и держала нарушение «сообщение об ошибке MUST быть понятно человеку» против FR-023. Поправка 3.0.0 заменила эту норму: отказ интерпретируется через задокументированный код, интерпретацию делает пользователь-сервис. Строка нарушения снята.

### До фазы 0

- **I. Расширяемость.** Границы сохраняются: домен доски не зависит от HTTP и PostgreSQL; новый домен учётки не ссылается на EF и HTTP; инфраструктура зависит от домена. Новый контракт — префикс `/v1`, старые `/api/board` и `/profiles` не переписываются молча. Ломающее изменение старого контракта не требуется. Одноразовый обход не подменяет репозиторий. Отдельный feature flag не нужен: новое поведение включено новыми маршрутами, старые маршруты остаются. **Пройдено.**
- **II. Надёжность.** Критический путь (авторизация, запись доски, миграция, смена секрета) закрывается тестами. Отказ явный, код стабильный. Тихой порчи нет: регистрация, смена имени, смена пароля, удаление и запись журнала идут одной транзакцией. Миграция обратима (`Down` снимает таблицы этой фичи), отдельный ADR необратимости не требуется. Пароль хранится только как хэш Identity V3. Секрет подписи JWT и пароли ролей базы не коммитятся. Чужой профиль и чужая доска не отдаются. Ошибка сервиса пишется структурным логом без пароля, хэша, токена и тела запроса. Готовность — `GET /v1/health/ready`. **Пройдено.**
- **III. Функциональность.** Объём — все истории, не срез. Ввод проверяется до изменения состояния. Контракт, переменные окружения и шаг миграции описаны. Тело отказа — задокументированный код в [contracts/account-api.yaml](contracts/account-api.yaml). Вызывающий сервис интерпретирует код по русскому описанию в контракте. Конечный пользователь сырой код не разбирает. Код и документация не содержат пароль. CLI этой фичей не становится удалённым входом. Если CLI показывает отказ сервиса, он переводит код в понятное сообщение и возвращает ненулевой код выхода. **Пройдено.** Нарушения нет.
- **IV. Консистентность доменной модели.** Доска по-прежнему содержит колонки, колонка — карточки. У карточки id, title, необязательные description, tags и deadline, createdAt в UTC. Имя колонки уникально в доске, теги карточки уникальны, срок — `YYYY-MM-DD`. Новых полей карточки нет. Сравнение имён колонок и тегов без учёта регистра остаётся правилом ADR-0001 и не переносится на ник. Ник — сущность учётки, не карточки. **Пройдено.**
- **V. Spec-Driven Development.** Этот документ — шаг plan с проверкой I–V до проектирования и повторно после него. Реализация ещё не начата. Смена поведения при реализации обязана в том же изменении обновить `docs/` и добавить ADR о хранилище учётки в PostgreSQL (JSON из ADR-0001 остаётся хранилищем локального CLI, не доски владельца). ADR в этом шаге не пишется: поведение продукта ещё не меняется. **Пройдено.**

Целевой стек конституции (веб-API .NET, PostgreSQL, JWT, одна доска на пользователя) совпадает с планом. Файловое хранилище доски владельца не закрепляется.

### Повторно после фазы 1

Сверка с [data-model.md](data-model.md), [contracts/account-api.yaml](contracts/account-api.yaml), [contracts/operator-audit.md](contracts/operator-audit.md) и [quickstart.md](quickstart.md):

- В схеме ответа отказа нет поля фразы, нет ProblemDetails и нет пароля. Русские формулировки стоят в `description` контракта: это документация кода для вызывающего сервиса, не тело ответа. По конституции 3.0.0 так и должно быть. Нарушения III нет.
- Журнал владельца не хранит вторую копию ника, имени и пароля. Срок доступа не хранится отдельно от времени входа. Нового нарушения BCNF и принципа IV нет.
- Отдельная роль оператора и запрет UPDATE/DELETE журнала не добавляют группу и не открывают чужую доску.
- Пункт III про Vue SPA и доступность: эта фича не меняет экран и не публикует контракт фронтенда. Контракт, от которого будущий интерфейс зависит, даёт по одной ситуации один код и русскую формулировку в описании. Интерфейс выступает пользователь-сервисом и сам показывает смысл человеку. **Пройдено.**
- Нарушений I–V нет.

**Structure Decision**: HTTP этой фичи живёт в уже существующем `Kanban.Api`, чтобы не появлялся третий хост и вторая главная копия. Домен учётки — новые проекты `Account.Domain` и `Account.Infrastructure`: класть ник и пароль в `UserProfile.Domain` нельзя, там другая модель (почта, фото), а публичный `/profiles` нельзя молча сменить. `Kanban.Domain` не ссылается на Account и не узнаёт про PostgreSQL. Миграции EF лежат в `Account.Infrastructure`. Их применяет оператор строкой из quickstart, процесс API подключается ролью приложения и сам схему не создаёт (`EnsureCreated` для этой базы не используется). Образ базы — `docker/postgres`. Корневой `Dockerfile` по-прежнему публикует только API. CD дописывает в архив `Dockerfile`, `docker/postgres/Dockerfile` и `docker-compose.yml`, не меняя правило «релиз только по тегу».

При реализации в том же изменении: ADR `docs/adr/adr-0003-postgres-account-store.md` и правка `docs/`, где единственным хранилищем всё ещё назван только JSON. Это требование принципа V к смене поведения, не артефакт текущего шага.
