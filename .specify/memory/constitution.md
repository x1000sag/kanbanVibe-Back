# KanbanVibe Constitution

## Core Principles

### I. Расширяемость

Границы API, домена и инфраструктуры MUST оставаться явными.
Домен Board, Column и Card MUST NOT зависеть от HTTP, CLI или способа хранения.
Публичный контракт и схема данных MUST меняться через версию контракта или миграцию.
Ломающее изменение без ADR и плана совместимости MUST NOT приниматься.
Одноразовый обход MUST NOT закрывать границу, у которой уже есть интерфейс
или точка расширения.
Feature flag SHOULD применяться, когда поведение нужно включать отдельно от выкладки кода.

Обоснование: KanbanVibe — долгоживущий продукт. Смена хранения и авторизации
идёт через границы, а не через разовые правки.

### II. Надёжность

Критические пути MUST иметь тесты: авторизация, сохранение доски, миграции схемы
и запись состояния.
Ошибка MUST быть явной для вызывающей стороны. Тихая порча или потеря данных MUST NOT происходить.
Миграция схемы SHOULD быть обратимой. Необратимая миграция MUST сопровождаться ADR
и планом отката.
Auth MUST быть безопасным по умолчанию: пароль только в виде хэша, секрет не в репозитории.
Доступ к чужой доске и профилю MUST NOT предоставляться.
Ошибка сервиса MUST попадать в структурный лог. Сетевой сервис MUST предоставлять
проверку готовности.

Обоснование: сбой хранения или auth бьёт по данным пользователя. Тесты и логи
делают отказ видимым до поставки.

### III. Функциональность

Спецификация MUST поставляться целиком, включая граничные случаи, пустые состояния
и ошибки. Демонстрационный срез не считается выполнением сценария.
Сообщение об ошибке MUST явно интерпретироваться через задокументированный код ошибки.
Интерпретацию выполняет пользователь-сервис, а не конечный пользователь.
Код ошибки и его документация MUST NOT раскрывать секрет.
CLI при ошибке MUST возвращать ненулевой код выхода и понятное сообщение.
Если CLI вызывает сервис, он является пользователь-сервисом и MUST переводить
задокументированный код в это сообщение.
Ввод MUST проверяться на границе API и CLI до изменения состояния.
Контракт API, конфигурация и миграции MUST быть документированы для интегратора
и оператора.
Поведение, которое видит пользователь Vue SPA, MUST быть согласованным.
Требования доступности этого интерфейса MUST учитываться в контракте API,
от которого интерфейс зависит.

Обоснование: ценность продукта — законченный сценарий, а не частичный ответ API.
Смысл отказа для человека собирает пользователь-сервис по задокументированному коду.
Конечный пользователь сырой ответ не интерпретирует.

### IV. Консистентность доменной модели

Код, спецификации, ADR и документация MUST описывать одну модель: Board, Column, Card.
Пока спецификация не изменила модель, доска содержит колонки, колонка — карточки,
а карточка содержит id, title, необязательные description, tags и deadline, а также createdAt.
Имя колонки MUST быть уникальным в пределах доски.
Идентификатор карточки MUST быть уникальным. Теги одной карточки MUST быть уникальны.
Срок карточки, если задан, MUST использовать дату YYYY-MM-DD.
Время создания MUST храниться в UTC.
Изменение инварианта MUST проходить через спецификацию и ADR, а не через локальное исключение.

Обоснование: CLI, API и Vue SPA читают одну модель. Расхождение артефактов ломает контракт.

### V. Spec-Driven Development

Новая функциональность MUST идти циклом Spec Kit:
constitution, specify, clarify, plan, tasks, implement.
План MUST содержать Constitution Check по принципам I–V до проектирования
и повторно после него.
Мелкая правка дефекта и правка документации MAY идти без новой спецификации,
если поведение продукта и контракт не меняются.
Реализация MUST соответствовать spec.md, plan.md и tasks.md фичи.
Смена поведения MUST обновлять docs/ и ADR в том же изменении.

Обоснование: конституция и спецификация задают объём. Код не опережает их.

## Технологический стек и целевая архитектура

KanbanVibe — профессиональный продукт. Учебный прототип не задаёт норму качества.

Текущая база репозитория: C# / .NET, solution kanban-cli/Kanban.sln, тесты xUnit.
Сейчас доска читается из JSON, профиль — из SQLite, CLI остаётся локальным клиентом домена.
Это переходное состояние, а не норма продукта.

Целевая архитектура, которой MUST соответствовать новые спецификации:
веб-API на .NET, Vue SPA в репозитории kanbanVibe-front, PostgreSQL,
учётная запись и JWT, одна доска на пользователя.
Файловое хранилище доски MUST NOT закрепляться как целевое.
Новая персистентность MUST проходить через границу инфраструктуры и миграции.

Язык артефактов — русский: конституция, спецификации, ADR и документация кодов
ошибки, по которой пользователь-сервис строит интерпретацию. Сообщение CLI для
человека тоже на русском. Идентификаторы кода следуют конвенциям .NET.

## Правила поставки

Объём фазы MUST фиксироваться спецификацией. Дорожная карта задаёт направление
и MUST NOT подменять спецификацию и MUST NOT снижать планку принципов I–III.
Формулировки «достаточно для занятия», «минимальный MVP» и YAGNI MUST NOT быть основанием
пропустить тесты критического пути, явную ошибку, миграцию, версию контракта
или граничный случай указанного сценария.
Незапрошенная подсистема MUST NOT добавляться без спецификации.
Обратная совместимость опубликованного контракта MUST сохраняться,
пока спецификация или ADR явно не вводит версию и миграцию.

## Governance

Конституция MUST иметь приоритет над README, ADR, спецификациями и AGENTS.md
при расхождении. Другие документы приводятся к ней, а не наоборот.
Поправка MUST проходить через /speckit.constitution, а не через правку шаблонов Spec Kit.
Версия SHOULD расти так: MAJOR — снятие или несовместимое переопределение принципа;
MINOR — новый принцип или существенное расширение правила; PATCH — уточнение без смены нормы.
Дата ратификации не меняется. Дата поправки — день принятого изменения.
Правка, которая меняет правила для агентов, MUST синхронизировать AGENTS.md,
если файл повторяет эти правила.
Ревью MUST проверять Constitution Check. Нарушение принципа MUST быть
явно обосновано в плане либо устранено до реализации.
Шаблоны .specify/templates/ MUST NOT редактироваться ради смены принципов:
их читает Spec Kit 1.2.3 в рантайме.
